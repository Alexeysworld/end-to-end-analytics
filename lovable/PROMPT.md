# Промпт для Lovable: дашборд сквозной аналитики

Собирайте итерациями, а не одним сообщением. Каждый шаг ниже — отдельный промпт
в чат Lovable. Ждите, пока предыдущий соберётся и вы посмотрите результат.
Одним огромным сообщением Lovable выдаёт правдоподобную, но неверную в деталях
сборку, и разбирать её дороже, чем собирать по шагам.

Перед шагом 1 приложите к чату файл `dataset.json` (241 КБ). Если загрузка
файлов недоступна — вставьте текстом `dataset.compact.json` (70 КБ), но учтите,
что в нём нет групп, запросов, недельной динамики и брендов внутри кампаний,
поэтому шаги 4 и 6 на нём не соберутся.

## Шаг 0. Установка рамок

```
Собираем внутренний прототип BI-отчёта. Это рабочий инструмент аналитика,
не лендинг и не маркетинговый дашборд.

Стек: React + TypeScript + Tailwind + Recharts. Данные — приложенный
dataset.json, положи его в src/data/dataset.json и типизируй.
Никакого бэкенда, авторизации, роутинга по страницам и загрузки данных
по сети. Всё локально, всё синхронно.

Жёсткие требования к оформлению, они важнее красоты:

1. Плотность как в BI-интерфейсе. Базовый кегль 13px, строка таблицы
   не выше 28px, отступы в ячейках 8px по горизонтали и 5px по вертикали.
2. Все табличные числа — моноширинным начертанием, выравнивание по правому
   краю, font-variant-numeric: tabular-nums, единый формат разрядов
   (узкий пробел между тысячами, минус — символ U+2212).
3. Цветом кодируется ТОЛЬКО знак результата: зелёный для положительного,
   красный для отрицательного. Ничего больше не раскрашиваем.
4. Никаких карточек с тенями, скруглений больше 6px, градиентов,
   больших плиток KPI и декоративных иконок. Блоки — прямоугольники
   с рамкой 1px.
5. Не используй компоненты shadcn/ui с их дефолтными отступами: они втрое
   разреженнее, чем нужно. Пиши разметку и стили руками.
6. Работает от 1280px. Мобильную адаптацию не делай вообще.
7. Интерфейс на русском. Никаких emoji в интерфейсе.

Палитра: нейтральная серая шкала с холодным уклоном для текста и рамок,
зелёный #0f7b4f для положительного знака, красный #b3261e для
отрицательного, синий #2f5fd8 как акцент для интерактивных элементов.
Для трёх каналов покупки: сайт #2a78d6, приложение #eb6834, офлайн #1baf7a.
Больше хроматических цветов нигде не появляется.

Сейчас ничего не верстай. Ответь только: какие поля есть в dataset.json,
как связаны узлы через parentId и какие уровни иерархии в нём есть.
```

Проверьте ответ: Lovable должен назвать уровни `source`, `placement`,
`campaign`, `adgroup`, `keyword` и сказать, что у каждого узла есть блоки
`first` и `all`. Если он этого не увидел — данные не подхватились, дальше
идти нет смысла.

## Шаг 1. Каркас и переключатель горизонта

```
Сделай каркас приложения.

Шапка в одну строку: название «Сквозная аналитика», рядом серым
meta.advertiser и meta.periodLabel, плашка «прототип на синтетических
данных».

Под шапкой вкладки: Сводка · Окупаемость · Товарная аналитика ·
Каналы покупки. Активная вкладка подчёркнута снизу линией 2px.
Пока покажи только заглушки.

Справа в шапке — главный элемент интерфейса: переключатель горизонта
окупаемости из двух положений, «Первый заказ» и «Все покупки клиента».
Это сегментированный контрол: активное положение — тёмный прямоугольник
с белым текстом, индикатор ЕЗДИТ между положениями с анимацией 300ms.
Позицию индикатора считай по реальным offsetLeft и offsetWidth кнопок,
а не по долям ширины: подписи разной длины, и доли разъезжаются.

Горизонт — глобальное состояние всего приложения. Он выбирает, какой блок
метрик читать у каждого узла: first или all. Никаких пересчётов на клиенте,
всё уже посчитано в данных.

Рядом с переключателем — подпись, которая меняется вместе с ним:
— на «Первый заказ»: сколько кампаний выглядят убыточными и сколько
  бюджета попадает под сокращение;
— на «Все покупки клиента»: сколько кампаний окупается позже и какая
  доля бюджета этим спасена.
Считай так: кампания «меняет решение», если first.roi < 0 и all.roi >= 0.
```

## Шаг 2. Таблица окупаемости — главный экран

```
Вкладка «Окупаемость». Одна таблица с разворачиванием строк внутри себя,
без перехода на отдельные страницы.

Иерархия: источник → тип размещения → кампания → группа → запрос.
Собирай дерево из плоского nodes по parentId. Уровень placement есть только
у Яндекс Директа — у остальных источников кампании висят прямо на источнике.
Глубина ветки поэтому разная, это нормально, не выравнивай её.

Колонки слева направо:
название (с отступом по уровню и кнопкой + / − для разворачивания),
расход, клики, CPC, заказы, [раскладка по каналу], выкупленные заказы,
доход от выкупленных, маржа, CPO, % повторных, ROI.

Под числом выкупленных заказов мелким серым — доля выкупа (buyoutRate).
Если она меньше 75%, красим эту долю красным.
Под значением ROI мелким серым — прибыль (profit) со знаком.

Раскладка по каналу покупки — переключатель из трёх режимов над таблицей:
— «Всего» — колонок канала нет;
— «Онлайн / офлайн» — две колонки: onlineOrders и ordersByChannel.offline;
— «Сайт / прил. / офлайн» — три колонки из ordersByChannel.
По умолчанию «Онлайн / офлайн»: сайт и приложение объединены.
Под каждым числом заказов мелким серым — доля канала из channelShare.
Колонки канала выделены очень слабой синей подложкой.

Сортировка по клику на заголовок любой колонки, в обе стороны.
Сортируй внутри каждого уровня отдельно, дерево при этом не ломается.
Чекбокс «только убыточные» — прячет кампании с ROI >= 0 вместе с их
потомками, но источники и размещения оставляет.

Строки с отрицательным ROI помечены узкой красной полосой 2px у левого края.
Фон строк не заливаем.

Перед итоговой строкой — отдельная строка «Не атрибуцировано» на бледно-жёлтом
фоне: заказы и доход из totals.unattributed, а в колонках расхода, CPC, CPO
и ROI стоят прочерки. Подпись под названием: «Клиент не идентифицирован или
окно атрибуции истекло. В ROI не входит — ни в числитель, ни в знаменатель».
Это принципиально: неатрибуцированное нельзя размазывать по каналам
и нельзя включать в ROI.

Итоговая строка — прилипшая к низу таблицы, значения из totals.
Заголовок таблицы прилипший к верху.

Переключение горизонта должно читаться как смена решения:
— строки, у которых знак ROI изменился, на короткое время подсвечиваются
  вспышкой синего фона (1.1s, затухает);
— на горизонте «все покупки» у таких строк рядом с ROI появляется старое
  значение мелким серым зачёркнутым и бейдж «окупается на повторных»;
— на горизонте «первый заказ» ни зачёркнутых значений, ни бейджей нет.
Это важно: если ответ виден заранее, переключатель нечего нажимать.

Бейджи на строке, когда есть повод:
— unattributedShare > 20% → жёлтый «н/атр. NN%»;
— buyoutRate < 75% → красный «возвраты NN%».

Клик по названию кампании пока ничего не делает, карточку сделаем дальше.
```

## Шаг 3. Карточка кампании

```
Клик по названию кампании открывает модальное окно шириной 1180px,
закрывается по Esc и по клику вне окна.

Шапка карточки: хлебные крошки sourceName › placementName, название
кампании, плашки с категорией и маржинальностью.

Полоса метрик по текущему горизонту в один ряд: расход (и CPC мелким),
клики, заказы, выкуплено (и доля выкупа), доход от выкупленных, маржа,
CPO (и CPO по выкупу), % повторных, ROI крупно со знаком.

Ниже — текстовый вывод, собранный ИЗ ДАННЫХ, не из заготовленных фраз.
Правила, по порядку:
1. Если first.roi >= 0 — «Окупается уже на первом заказе: ROI …, на всех
   покупках …. Ставку можно поднять с {first.cpc} ₽ до {first.breakEvenCpc} ₽
   по первому заказу и до {all.breakEvenCpc} ₽ с учётом повторных».
2. Иначе, если в paybackCurve есть точка с roi >= 0 — «Окупается на N-м
   заказе: по первому заказу ROI …, по всем покупкам …. Повторяемость … —
   именно она вытаскивает кампанию в плюс».
3. Иначе, если repeatRateGapToBreakEven > 0 — «Убыточна на всём горизонте:
   … До безубыточности не хватает N п.п. повторяемости».
4. Плюс отдельная строка, если buyoutRate < 80%: «Возвраты забирают N%
   заказанной выручки: по заказанному ROI был бы {roiBeforeReturns},
   по факту выкупа {roi}. Проблема в размерах, а не в ставке».
5. Плюс строка, если доля приложения и офлайна вместе > 40%: «N% покупок
   происходит вне сайта: … в приложении и … в офлайне. Сквозная аналитика
   по куке видела бы только веб — там ROI {webOnlyRoi}».
6. Плюс строка, если unattributedShare > 20%: «N% покупок не связано
   с источником … Эти заказы в ROI не входят, фактическая окупаемость
   не хуже показанной».
Каждая строка — с цветной полосой 2px слева по смыслу: зелёная, синяя,
жёлтая, красная.

Дальше четыре блока.

Блок 1, недельная динамика из weeks. ДВА графика друг под другом,
а не две шкалы на одном — двойные оси врут:
— сверху: столбцы расхода (серые, скругление 4px сверху, ширина до 26px)
  и линия маржи (тёмная, 2px), обе величины в рублях, одна шкала.
  Ось X у верхнего графика скрыта;
— снизу: столбцы ROI недели, зелёные выше нуля и красные ниже,
  с линией нуля. Ось X подписана здесь.
Отступы и ширина оси Y у обоих графиков одинаковые, чтобы колонки стояли
друг под другом. Причина второго графика: зазор между линией и столбцами
бывает порядка десяти процентов, глазом такую разницу по тринадцати
неделям не сложить.

Блок 2, кривая окупаемости из paybackCurve: накопленный ROI к первому,
второму и третьему заказу. Линия тёмная 2px, точки окрашены по знаку,
подписи значений у всех трёх точек (их всего три, и это само сообщение
графика), серая горизонтальная линия нуля. Под графиком — «Точка
безубыточности пройдена на N-м заказе» или «Безубыточность не достигается
даже к третьему заказу».

Блок 3, покупки по каналу: одна горизонтальная полоса с тремя сегментами
и зазором 2px между ними, под ней таблица из трёх строк — канал, заказы,
доля, доход от выкупленных. Плюс отдельная строка неатрибуцированного
на бледно-жёлтом фоне. Подписи каналов обязательны текстом: у зелёного
низкий контраст на белом, цвет один не справляется.

Блок 4, запас по ставке: горизонтальная полоса, залитая до текущего CPC,
и два маркера — сплошной на break-even текущего горизонта, пунктирный
на break-even другого. Ниже три числа: текущий CPC, break-even CPC,
и «можно поднять на +N ₽» либо «надо снизить на −N ₽».
Показывай в РУБЛЯХ, а не в процентах: процентный запас математически
тождественен ROI (break-even CPC / CPC − 1 = маржа / расход − 1)
и дублировал бы цифру из шапки.
```

## Шаг 4. Каналы покупки

```
Вкладка «Каналы покупки». Отвечает на один вопрос: сколько выручки
не видно без приложения и офлайна.

Верхний блок, четыре метрики: доход вне сайта (приложение плюс офлайн,
в рублях и в процентах от общего), заказы вне сайта, сколько кампаний
меняют решение при переходе от веб-взгляда к полным данным, доля
неатрибуцированного.

Центральный блок — сравнение двух взглядов по каждой кампании на ОБЩЕЙ
горизонтальной шкале, отсортированное по расходу:
— светлая пустая точка — webOnlyRoi: ROI, каким его видит аналитика
  по куке, то есть только покупки на сайте и только первый заказ;
— закрашенная точка — ROI на полных данных по текущему горизонту,
  цвет по знаку;
— между ними серый отрезок 2px. Длина отрезка — это и есть то,
  что отчёт добавляет к картине;
— вертикальная линия нуля проходит через все строки на одной позиции,
  подписана «0% — безубыточность» один раз сверху;
— справа от точек — оба значения текстом: полное цветом по знаку,
  веб-значение серым после стрелки;
— бейдж «меняет решение» у строк, где webOnlyRoi < 0, а полный ROI >= 0.

Нижний блок — таблица: источник, разворачивается до кампаний. Слева
заказы по трём каналам с долями, посередине микро-полоса раскладки,
справа доход от выкупленных заказов по трём каналам, доля
неатрибуцированного и ROI.

В подвале таблицы обязательно: «Неатрибуцированные покупки в раскладку
по каналам не входят: источник для них неизвестен, поэтому их нельзя
отнести ни к вебу, ни к приложению, ни к офлайну».
```

## Шаг 5. Сводка

```
Вкладка «Сводка», она же первый экран. Не набор KPI-плиток.

Верхний блок «Где я теряю деньги». Слева — два больших числа рядом:
ROI по первому заказу (красный) и ROI по всем покупкам (зелёный),
кегль около 30px, между ними подпись «разрыв N п.п.» и стрелка.
Под каждым мелким серым — маржа и расход.
Смысл, который должен считываться: расход один и тот же, разница только
в том, до какого заказа считать окупаемость.

Справа три метрики:
— «Бюджет под ложным сокращением»: сумма расхода кампаний, у которых
  first.roi < 0 и all.roi >= 0, с их числом и долей от общего расхода;
— «Реально убыточный бюджет»: сумма расхода кампаний с all.roi < 0
  и сколько они теряют;
— «Данные, которых не видно по куке»: доля дохода из приложения
  и офлайна плюс доля неатрибуцированного.

Под этим — горизонтальная полоса всего расхода, разбитая на три группы
решений с процентами внутри сегментов и легендой под ней:
— «Докупить или держать» (зелёный): first.roi >= 0;
— «Не резать» (синий): first.roi < 0 и all.roi >= 0;
— «Отключить» (красный): all.roi < 0.

Ниже три колонки-списка под эти же три решения. В каждой строке:
название кампании, источник, расход, ROI по текущему горизонту.
И цена вопроса второй строкой мелким серым, разная для каждой группы:
— «отключить» — сколько теряет;
— «не резать» — сколько даёт на повторных;
— «докупить» — до какой ставки можно поднимать: «ставка 39 → 133 ₽».
Сортировка: «отключить» по величине потерь, «не резать» по расходу,
«докупить» по ROI.

Замыкающий блок «Чему в этих числах можно верить», четыре пункта:
неатрибуцировано, возвраты и отмены, горизонт данных (три заказа),
модель атрибуции (last-click по клиенту в едином профиле, а не по куке).
Этот блок нужен не для галочки: без него отчёту не поверят.
```

## Шаг 6. Товарная аналитика

```
Вкладка «Товарная аналитика». Данные: brandTotals для аккаунта и
nodes[кампания].brands для разворачивания.

Слева блок из четырёх метрик: доход от выкупленных заказов и средняя
маржинальность, доля СТМ в доходе (бренд с kind = «СТМ»), худший бренд
по ROI, худший по возвратам.

Справа — полосы ROI по брендам от нуля в обе стороны, отсортированные
по убыванию, с подписью значения справа.

Ниже таблица брендов: бренд с плашкой типа, заказы, выкупленные заказы
и доля выкупа, доход от выкупленных и доля в общем доходе, средний чек,
маржинальность, возвраты, % повторных, расход (распр.), ROI.

В подвале обязательно: «Бренд — разложение уже посчитанных чисел запроса,
а не отдельный расчёт: суммы по брендам точно равны итогам таблицы
окупаемости. Расход рекламы живёт на запросе, а бренд на товаре, поэтому
расход распределён внутри каждого запроса пропорционально заказам —
иначе носки платили бы за клик по кожаной куртке».
```

## Шаг 7. Заметки ревью

```
Добавь сбор обратной связи по прототипу.

У заголовка каждого блока и у ключевых колонок — маленькая иконка
комментария. Клик открывает поповер: список уже оставленных заметок
к этому блоку и поле для новой, сохранение по ⌘↵.

Заметка хранит: идентификатор и название блока, экран, текст, время,
и СОСТОЯНИЕ ОТЧЁТА на момент написания — выбранный горизонт, режим
раскладки по каналам, открытую кампанию. Без состояния комментарий
«тут непонятно» потом невозможно привязать к тому, что человек видел.

Кнопка в шапке открывает панель со всеми заметками, сгруппированными
по экранам, и кнопкой «Выгрузить JSON». Заметки живут в localStorage.
```

## Что не делать

Скажите Lovable это прямо, иначе он добавит сам:

```
Не добавляй: авторизацию, настройки, выбор периода, фильтры по датам,
экспорт в Excel, подключение к реальным источникам, атрибуционные модели
кроме last-click, прогнозы, рекомендации по офферам и промокодам,
онбординг, тултипы-подсказки «что это за метрика» на каждой колонке,
светлую и тёмную темы, анимации переходов между вкладками.
```

## Как проверить, что получилось

Прототип собирают ради четырёх вопросов. Проверяйте по ним, а не по
количеству экранов:

1. Понимает ли маркетолог за 10 секунд, какие кампании отключить,
   а какие докупить?
2. Считывается ли переключение «первый заказ / все покупки» как смена
   решения, а не как смена цифры?
3. Не выглядит ли раскладка по каналам покупки лишней сложностью?
4. Достаточно ли честно показана неатрибуцированная часть, чтобы
   отчёту доверяли?

Контрольные числа — если они не сходятся, Lovable где-то пересчитал
данные вместо того, чтобы их прочитать:

| Что | Значение |
|---|---|
| Расход по аккаунту | 3 188 219 ₽ |
| ROI по первому заказу | −7,0% |
| ROI по всем покупкам | +27,4% |
| Заказы на первом горизонте | 1 861 |
| Выкупленные заказы | 1 545 |
| Доход от выкупленных | 11,2 млн ₽ |
| Доля неатрибуцированного | 15% |
| Кампаний «меняют решение» | 5 из 15 |
| Расход этих пяти | 1 743 149 ₽ (55%) |
| ROI «Куртки» | −11,0% → +15,9% |
| ROI «Штаны и брюки» | −24,0% → +1,1%, выкуп 68% |
| ROI «Бренд» | +115,0% → +241,1% |
| webOnlyRoi «Бренд» | −16,3% |

Последняя строка — самый сильный кадр в отчёте: брендовая кампания
с ROI +115% выглядит убыточной, если считать только покупки на сайте,
потому что половина её покупок происходит в мобильном приложении.
