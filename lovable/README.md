# Материалы для сборки дашборда в Lovable

| Файл | Что это | Размер |
|---|---|---|
| `PROMPT.md` | Промпт, разбитый на восемь шагов. Каждый шаг — отдельное сообщение в чат. | — |
| `dataset.json` | Полный датасет. Приложите файлом к чату перед первым шагом. | 245 КБ |
| `dataset.pretty.json` | То же с отступами — для чтения глазами, в Lovable не нужен. | 409 КБ |
| `dataset.compact.json` | Только источники, размещения и кампании. Для случая, когда файл загрузить нельзя и датасет приходится вставлять текстом. | 73 КБ |

Пересобрать данные: `npm run export:lovable`.

## Главное решение в этих данных

Выгружены **уже посчитанные** метрики по каждому узлу, отдельно для двух
горизонтов окупаемости (`first` и `all`). Не сырые клики с формулами.

Причина: если принимающая сторона считает арифметику сама, она её реализует
чуть иначе — округление, порядок агрегации, обработка нулей — и цифры разойдутся
с нашим прототипом. Тогда две версии станет невозможно сравнить, а прототип
собирается именно ради сравнения подачи, не ради арифметики.

Поэтому в промпте прямо сказано: ничего не пересчитывать, только читать поля.
В конце промпта есть таблица контрольных чисел — по ней видно, если Lovable
всё-таки полез считать.

## Структура датасета

```
meta                 период, рекламодатель, сид, определения метрик
purchaseChannels     три канала покупки: web / app / offline
categories           товарные категории: чек, маржинальность, доля выкупа
brands               10 товарных брендов
totals.first|all     итоги по аккаунту для каждого горизонта
totals.unattributed  неатрибуцированные покупки по аккаунту
brandTotals.first|all товарные бренды по аккаунту
nodes[]              плоский список 114 узлов, дерево через parentId
```

Каждый узел в `nodes`:

```
id, parentId, level, name        level: source | placement | campaign | adgroup | keyword
note                             только у некоторых запросов: почему запрос ведёт себя так
first { … }                      метрики по первому заказу
all   { … }                      метрики по всем покупкам клиента
webOnlyRoi                       ROI, каким его видит аналитика по куке
```

Дополнительно только у кампаний:

```
fullName, sourceName, placementName, category, categoryId
marginRate                       фактическая маржинальность кампании
roiBeforeReturns                 ROI по заказанной выручке, до возвратов
paybackCurve[3]                  накопленный ROI к 1-му, 2-му, 3-му заказу
repeatRateGapToBreakEven         сколько п.п. повторяемости не хватает до нуля
weeks[13]                        недельная динамика
brands.first|all                 товарные бренды внутри кампании
```

Состав блока метрик (`first` и `all` одинаковы по полям):

```
clicks spend cpc
orders netOrders revenue netRevenue margin profit
cpo cpoNet aov roi buyoutRate repeatRate repeatOrdersShare breakEvenCpc
ordersByChannel{web,app,offline} netRevenueByChannel{…} channelShare{…}
onlineOrders onlineNetRevenue onlineShare
unattributedOrders unattributedNetRevenue unattributedShare
```

Деньги округлены до рубля, доли — до четырёх знаков. Заказы дробные: это
модельные величины, а не пересчёт физических чеков. В интерфейсе округляйте
их до целого, а значения меньше единицы печатайте как `<1` — «0» рядом
с подписью «9%» читается как ошибка в данных.

## Чего в данных нет

- Периода и разбивки по датам, кроме недельной динамики у кампаний.
- Атрибуционных моделей, кроме last-click по клиенту в едином профиле.
- Заказов дальше третьего: горизонт `all` — это первый, второй и третий+.
- Распределения неатрибуцированных покупок по каналам. Источник для них
  неизвестен, поэтому отнести их к каналу нельзя — в интерфейсе они живут
  отдельной строкой без ROI.

Допущения генератора и список произвольно взятых чисел — в README в корне
репозитория.
