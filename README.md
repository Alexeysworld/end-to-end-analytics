# Прототип отчёта сквозной аналитики Mindbox

Кликабельный прототип для внутренней валидации интерфейса. Проверяем, понятен ли
перфоманс-маркетологу способ подачи данных и приводит ли отчёт к решению о бюджете.

**Это не продакшн.** Бэкенда нет, реальные данные не подключены, все числа —
синтетический генератор с фиксированным сидом.

```bash
npm install
npm run dev        # http://localhost:5173
```

Интерфейс рассчитан на ширину от 1280px, мобильной адаптации нет — сознательно.

Дополнительно:

```bash
npm run data:sample   # печатает пример строки по каждому уровню иерархии
                      # и проверяет, что суммы по брендам сходятся с таблицей
npm run typecheck
```

## Что проверяет прототип

1. Понимает ли маркетолог за 10 секунд, какие кампании отключить, а какие докупить?
2. Считывается ли переключение «первый заказ / все покупки» как смена решения,
   а не как смена цифры?
3. Не выглядит ли раскладка по каналам покупки лишней сложностью?
4. Достаточно ли честно показана неатрибуцированная часть, чтобы отчёту доверяли?

Под каждым блоком есть иконка комментария: заметка складывается в локальный стейт
вместе с состоянием отчёта (горизонт, режим каналов, открытая кампания) и
выгружается в JSON кнопкой «Заметки ревью» в шапке.

## Модель клиента

Интернет-магазин одежды «Северный склон» с мобильным приложением и сетью офлайн-точек.
Период — 13 недель, 19 мая — 17 августа 2026.

Иерархия: **источник → тип размещения → кампания → группа → запрос**.
Уровень размещения есть только у Яндекс Директа (Поиск и РСЯ) — у VK, Telegram
и блогеров делить нечего, там кампании висят прямо на источнике. Глубина ветки
поэтому разная, таблица это допускает.

4 источника · 15 кампаний · 29 групп · 64 запроса · 10 товарных брендов.

## Как устроен генератор

| Файл | Роль |
|---|---|
| `src/data/specs.ts` | Товарные категории и спеки кампаний. **Единственное место, где числа заданы руками.** |
| `src/data/brands.ts` | Товарные бренды и их доли по категориям. |
| `src/data/generate.ts` | Детерминированный генератор (mulberry32, сид `20260819`). |
| `src/data/metrics.ts` | Производные метрики. В данных не хранятся, считаются на лету. |
| `src/data/types.ts` | Типы. |

Все числа считаются **на листьях** иерархии (запрос), узлы выше — сумма листьев.
Поэтому при разворачивании строк цифры всегда сходятся, и нет отдельной «правды»
на уровне кампании.

### Обратный счёт конверсии

Конверсия не задаётся, а **выводится из целевого ROI**:

```
roi = (cr · aov · buyout · marginRate) / cpc − 1
  ⇒  cr = (1 + targetRoiFirst) · cpc / (aov · buyout · marginRate)
```

После разброса по запросам ROI кампании **пинуется** к `targetRoiFirst`:
считается поправка на уровне кампании и применяется ко всем её запросам, поэтому
разброс внутри кампании сохраняется, а итог кампании точно попадает в заданную
зону. Без этого «пограничная» кампания уезжала с +6% на +20% и перестала быть
пограничной.

## Допущения, зашитые в генератор

Это то, о чём спросят на обсуждении в первую очередь.

### Атрибуция

- **Только last-click по клиенту в едином профиле.** Других моделей нет.
- **Неатрибуцированные покупки считаются по каждому узлу.** Это модельная оценка:
  в реальности связь с источником потеряна, и распределить эти покупки по кампаниям
  строго нельзя. Сделано так, чтобы было видно, что у блогеров потерь втрое больше,
  чем у бренда. Альтернатива — показывать только на уровне аккаунта: честнее,
  но сравнение источников по качеству идентификации пропадает.
- Неатрибуцированное **никогда не входит в ROI** — ни в числитель, ни в знаменатель.
  В таблице это отдельная строка с прочерками вместо расхода, CPO и ROI.
- Неопознанные покупки чаще офлайновые (48% против 15% в среднем): на кассе клиента
  опознать сложнее. Числа взяты произвольно.

### Горизонт окупаемости

- Когорты заказов: **первый, второй, третий и последующие**. Дальше третьего не считаем.
- `orders₂ = orders₁ · repeatRate`, `orders₃ = orders₁ · repeatRate² · 0.8`.
  Коэффициент затухания **0.8 взят произвольно**.
- Средний чек повторных заказов выше: ×1.05 на втором, ×1.10 на третьем.
  Доля выкупа лучше: +2.5 п.п. и +4 п.п. Оба множителя **произвольны**.
- Повторные покупки смещаются в приложение и офлайн: +7 п.п. и +4 п.п. на каждый
  следующий заказ, за счёт веба. Обоснование — программа лояльности живёт там.
  Величины сдвига **произвольны**.

### ROI

```
ROI = маржа / расход − 1        (0% — точка безубыточности)
```

Маржа считается от выручки **по факту выкупа**, не от заказанной.

Следствие, о котором стоит знать: **запас по ставке в процентах тождественен ROI**,
потому что `break-even CPC / CPC − 1 = маржа / расход − 1`. Поэтому в карточке
кампании запас показан в рублях ставки, а не в процентах — процент дублировал бы
цифру из шапки и выглядел бы как баг.

### Товарные бренды

Бренд — это **разложение уже посчитанных чисел запроса**, а не независимый расчёт.
Доли задают, кому достались заказы; множители бренда — насколько он отличается
от среднего по запросу. После разложения суммы нормируются, поэтому итог по брендам
точно равен итогам кампании. Скрипт `npm run data:sample` это проверяет.

Побочный эффект нормировки: маржинальность конкретного бренда слегка уезжает от
заявленного множителя. Соотношения между брендами сохраняются, абсолютные значения — нет.

**Расход на бренд распределяется внутри каждого запроса пропорционально числу
заказов.** Два следствия, оба намеренные:

- носки не платят за клик по кожаной куртке — у каждого запроса свой CPO;
- возвраты бьют по ROI бренда, а не маскируются. При распределении по доходу от
  выкупа бренд с возвратами получал бы меньше расхода и выглядел бы нормально.

Это допущение, а не факт. В интерфейсе колонка подписана «расход (распр.)».

## Числа, взятые произвольно

Реклама живёт на запросе, товар — на заказе, поэтому связь между ними в моке
задана вручную. Ниже всё, что не выведено из формул.

### Товарные категории

| Категория | Ср. чек | Маржа | Выкуп |
|---|---|---|---|
| Куртки и верхняя одежда | 11 000 ₽ | 24% | 86% |
| Штаны и брюки | 5 400 ₽ | 31% | **68%** |
| Аксессуары: носки, ремни | 2 100 ₽ | **38%** | 94% |
| Микс — весь ассортимент | 7 600 ₽ | 29% | 83% |
| Спецодежда оптом | 92 000 ₽ | 15% | 80% |

Два отклонения от исходного брифа, оба сознательные:

- **Выкуп штанов 68%** вместо заявленных «5–15% отмен и возвратов». В онлайн-продаже
  брюк и джинсов возвраты по размеру заметно выше, и это второй сюжет отчёта рядом
  с горизонтом окупаемости: кампания может быть убита размерной сеткой, а не ставкой.
  По аккаунту выкуп выходит 83% — в исходную вилку не попадает.
- **Маржинальность аксессуаров 38%** вместо вилки 25–35%. Нужна категория с высокой
  маржинальностью, чтобы был виден контраст с куртками.

### Диапазоны

- CPC: от 15 до 1500 ₽, жёстко ограничен после шума.
- Повторяемость: 6–44% по кампаниям.
- Доля покупок в приложении: 3–66% по кампаниям, ~30% в среднем по аккаунту.
- Доля неатрибуцированного: 9–29% по кампаниям, 15% по аккаунту.
- Шум по запросам: CPC ±14%, конверсия ±18%, средний чек ±10%, выкуп ±4%,
  повторяемость ±18%, доли каналов ±22–30%.
- Тренд расхода за 13 недель: множитель 0.8–1.3 на кампанию плюс шум ±14%.
- Эффективность по неделям плавает независимо от расхода (±18%) — иначе график
  недельной динамики скучный и ничего не показывает.

### Кампании

Каждой кампании задан **целевой ROI первого заказа**, чтобы в данных гарантированно
были все интересные для обсуждения типы:

| Тип | Кампании |
|---|---|
| явно прибыльные | Бренд +115%, Ретаргетинг +74%, Ретаргет VK +52%, Фид +38%, Промокоды +34%, Носки и ремни +30% |
| явно убыточные | Спецодежда −62%, РСЯ Широкий −46%, Интересы VK −39% |
| **разворот решения** | Куртки −11% → +16%, Макро-инфлюенсеры −26% → +15%, LAL VK −12% → +23%, TG тематические −8% → +24% |
| убивают возвраты | Штаны −24% при выкупе 68%; по заказанной выручке было бы +12,5% |
| много неатрибуцированного | TG скидки 27% — и остаётся убыточной даже с этой поправкой |
| разная экономика внутри | Куртки: «куртка дешёвая» −58% против «куртка кожаная» +20% |

Последняя строка — то, ради чего нужен drill-down: резать надо запрос, а не кампанию.

Итог по аккаунту: расход 3,2 млн ₽, ROI **−7,0%** по первому заказу и **+27,4%**
по всем покупкам. 55% бюджета сидит в кампаниях, которые выглядят убыточными
и окупаются на повторных.

## Цвет и типографика

- Табличные цифры моноширинные, по правому краю, единый формат разрядов.
  Всё от тысячи и выше — в тыс/млн одним правилом.
- Цветом кодируется **только знак результата**. Хроматика (синий / оранжевый /
  аквамарин) отдана каналам покупки, где нужна идентичность.
- Палитра графиков проверена валидатором из гайда по визуализации на белой
  поверхности. Пара зелёный/красный имеет CVD ΔE 6.5 — цвет не может быть
  единственным носителем знака, поэтому знак всегда дублируется символом `+/−`
  и положением относительно нулевой линии.
- Дробные значения меньше единицы печатаются как `<1`: «0» рядом с подписью «9%»
  читался как ошибка в данных.

## Вне рамок

Сознательно не сделано. Если понадобится — это отдельные задачи, не доработка.

| Что | Почему нет |
|---|---|
| Авторизация, настройки, роли | Прототип интерфейса, не продукт |
| Экспорт в Excel | Есть выгрузка заметок ревью в JSON, этого достаточно для обсуждения |
| Подключение к реальным источникам | Данных нет, генератор их заменяет |
| Атрибуционные модели кроме last-click | Отдельная большая тема |
| Сценарии коммуникаций и офферы под источник | У запросов есть поле `note` с пояснением, почему запрос ведёт себя так — например, что на «куртка дешёвая» промокод давать нельзя, маржинальность 13% меньше типичной скидки. Это заготовка под рекомендации, но самих рекомендаций в интерфейсе нет |
| Мобильная адаптация | Инструмент рабочего дня, от 1280px |
| Прогноз и планирование бюджета | Отчёт отвечает на «что было», не на «что будет» |
